# Точка выхода через звонки VK (для телефона на мобильной связи)

> ⚠️ **Только для личного использования.** Функция работает через серверы звонков VK и использует их
> не по назначению. Подключайте только свои устройства: один ПК, свой телефон, одна ссылка на звонок
> с одного аккаунта VK. Не раздавайте ссылку и QR-код, не делайте «общий сервер» для друзей или
> подписчиков и не выкладывайте готовые сборки с этим режимом как сервис. Массовое использование VK
> быстро заметит: аккаунт заблокируют, а способ закроют для всех. Лучше завести для этого отдельный
> аккаунт VK, а не основной.

## Зачем

На мобильной связи у части операторов действует белый список по IP: открыты только «российские»
сервисы, всё остальное режется ещё до DPI, поэтому обычный обход (byedpi/zapret) там бессилен.
Серверы звонков VK (TURN) в белом списке есть. Телефон занимает на них ретранслятор, домашний ПК —
тоже, и они обмениваются пакетами через VK. ПК дома выходит в интернет как обычно.

```
iPhone (LTE) ⇄ ретранслятор VK ⇄ ретранслятор VK ⇄ ПК дома ⇄ интернет
```

VPS и белый IP дома не нужны: обе стороны подключаются к VK как клиенты.

## Что нужно пользователю

1. ByeDPI PC на домашнем компьютере (Windows, macOS или Linux), включённый и в сети.
2. В настройках ByeDPI PC: «Точка выхода для телефона» → включить.
3. В VK создать ссылку на звонок («Звонки» → «Создать звонок» → «Скопировать ссылку»). Звонить не
   нужно: ссылка — просто «комната», звонок держать открытым не надо.
4. Дома по Wi-Fi: в ByeDPI на iPhone «Внешний прокси» → «Через ПК (звонки VK)» → вставить ссылку →
   «Связать с ПК» → отсканировать QR-код с экрана ПК. Если VK покажет «Я не робот» — нажать.
5. На мобильной связи всё работает само. Примерно раз в 8 часов телефон обновляет доступ к VK;
   если VK попросит капчу, придёт уведомление.

## Что выяснено проверками (октябрь 2026)

- Данные TURN выдаются по ссылке на звонок анонимно (цепочка как в vk-turn-proxy):
  `login.vk.ru ?act=get_anonym_token` → `calls.getCallPreview` → `calls.getAnonymousToken`
  (тут капча «Я не робот», ответ `error_code 14` с `redirect_uri`) → `calls.okcdn.ru auth.anonymLogin`
  → `vchat.joinConversationByLink` → `turn_server {urls, username, credential}`.
- Данные живут ~8 часов (`username` = `<unix-время окончания>:<id>`), выделение — 600 с с продлением.
- На одни данные — не больше 9 ретрансляторов одновременно («Allocation Quota Reached»).
  Освобождать: Refresh с LIFETIME=0. Иногда выдаётся «мёртвый» ретранслятор — проверять.
- Ретранслятор пропускает только пакеты, похожие на медиа звонка. Обычный текст выбрасывается.
  Пакеты вида **RTP** проходят до ~2 Мбит/с на один ретранслятор в каждую сторону; пакеты вида DTLS
  на скорости режутся почти полностью. Предел — на каждом ретрансляторе, поэтому используем несколько.
- С LTE открыты `login.vk.ru`, `api.vk.ru`, `id.vk.ru`, `calls.okcdn.ru` — телефон получает данные
  TURN и решает капчу сам, ПК браузер не нужен.

## Протокол (версия 1)

Обе стороны реализуют одно и то же: ПК — `ByeDpiPc.Core/VkRelay`, iPhone — `ByeDPIKit/VkRelay`.

### Роли и ключи

- Секрет связки `S` — 32 случайных байта, создаёт ПК, передаётся в QR-коде.
- Ключи направлений: `K_pc = HKDF-SHA256(S, salt="byedpi-vk-relay", info="pc->phone")`,
  `K_phone = HKDF-SHA256(S, salt="byedpi-vk-relay", info="phone->pc")`, по 32 байта.
- Шифр — ChaCha20-Poly1305.

### Пакет на проводе (данные внутри TURN Send/Data indication)

```
RTP-заголовок 12 байт:  0x80 | 0x6F | seq u16 | timestamp u32 | ssrc u32
счётчик          8 байт: u64, big-endian, растёт с каждым пакетом отправителя
шифртекст + тег 16 байт
```

- `ssrc` — случайное число, выбирается при запуске стороны; `seq = счётчик & 0xFFFF`,
  `timestamp = (счётчик * 960) & 0xFFFFFFFF`.
- Nonce (12 байт) = `ssrc` (4) + `счётчик` (8). AAD = RTP-заголовок.
- Получатель отбрасывает пакеты, которые не расшифровались.
- Размер пакета ≤ 1200 байт.

### Открытый текст

```
вид u8 | тело
```

| вид | тело |
|---|---|
| 1 HELLO | JSON `Hello` |
| 2 HELLO_ACK | JSON `Hello` |
| 3 KCP | один сегмент KCP |
| 4 PING | u64 время отправителя, мс |
| 5 PONG | u64 время из PING |

`Hello`:
```json
{ "v": 1, "role": "pc" | "phone", "node": "<id стороны>", "relays": ["ip:port", …],
  "creds": { "u": "…", "p": "…", "turn": ["ip:port", …] } | null, "session": <u32 conv KCP> }
```

- Телефон кладёт в HELLO свежие данные TURN (`creds`), ПК — нет.
- Каждая сторона запоминает последние `relays` собеседника (на диске) и после перезапуска
  шлёт HELLO на старые адреса, пока не получит HELLO_ACK.
- Разрешения (CreatePermission) обе стороны ставят на все IP серверов TURN из `creds.turn`:
  ретрансляторы собеседника живут на тех же IP.
- Связка дома: телефон шлёт тот же HELLO напрямую на `ip:порт` ПК в локальной сети из QR-кода
  (UDP, без TURN), ПК отвечает HELLO_ACK со своими ретрансляторами.

### Надёжная доставка и потоки

- Один сеанс KCP на связку (`conv` = `session` из HELLO телефона), сегменты рассыпаются по всем живым
  парам ретрансляторов: так один поток получает скорость нескольких ретрансляторов.
  Настройки: `nodelay=1, interval=10, resend=2, nc=0`, окна 512, MTU 1100.
- Поверх KCP — сообщения мультиплексора:

```
тип u8 | поток u32 | данные
```

| тип | данные |
|---|---|
| 1 OPEN | `host:port` (UTF-8), телефон → ПК |
| 2 OPEN_OK | — |
| 3 OPEN_FAIL | причина (UTF-8) |
| 4 DATA | байты потока (≤ 16 КБ) |
| 5 CLOSE | — |
| 6 CREDIT | u32: сколько ещё байт можно прислать |

- Начальный кредит потока — 256 КБ в каждую сторону; получатель возвращает CREDIT по мере чтения.
- ПК на OPEN сам подключается к `host:port` (DNS разрешает ПК) и гонит данные в обе стороны.
- UDP (QUIC) в версии 1 не передаётся — браузеры переходят на TCP.
